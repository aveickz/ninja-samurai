# Самураи против Ниндзя

Настольная карточная игра «Самураи против Ниндзя»: дизайн-документы по
механикам, веб-картотека для просмотра/печати карт и исходники полиграфии.
Онлайн-версия живёт отдельным репозиторием в соседней папке `online/`.

Настольная карточная игра «Самураи против Ниндзя»: веб-картотека для
просмотра/печати карт и дизайн-документы по механикам.

## Источники правды

- **Глобальные идеи и принципы дизайна** — `mechanics/meta_mechanics.md`.
  Самый важный файл проекта: задаёт мета-правила, по которым устроены
  все карты и механики. Любое решение по дизайну сверяется с ним в
  первую очередь. Начало файла содержит **North Star** проекта и
  сводный список 12+ мета-правил.
- **Правила игры** — `rules/rules.html`. Это полный и актуальный свод
  правил; всё, что в `mechanics/` или в обсуждениях, считается черновиком,
  пока не отражено здесь.
- **Карты колоды** — `js/cards.js`. Самые актуальные данные по каждой
  карте (название, тип, количество, текст эффекта, иконки, арт) живут
  именно в этом файле. Реестр в `mechanics/cards.md` — справочный слой
  для дизайн-обсуждений и может отставать; при расхождениях ориентируемся
  на `js/cards.js`.

## North Star проекта

> Вовлечь всех игроков в каждый ход и держать высокий темп, отражая
> динамичный бой самураев — а не размеренную турнирную партию.

При оценке любой новой механики первый вопрос: **«втягивает ли она
других игроков в момент или заставляет их ждать?»** Подробнее — в
`mechanics/meta_mechanics.md`, раздел «Главная цель игры».

## Антипаттерны — быстрый чеклист

При предложении новой механики проверять, что **ни одно из этого не
нарушено**. Полные определения — в `mechanics/meta_mechanics.md`.

- **Фоновые ауры персонажей / постоянные эффекты в чужой ход** (правило №12) — нет.
- **Замедляющий denial** («нельзя атаковать», «−1 карта в наборе») — нет; ускоряющий («нельзя защищаться») — ОК.
- **Каскадный урон в Deathrattle / On-Kill / Team Aura** — нет; используй статусы, лечение, передачу ресурсов.
- **Открытые эффекты закрытых карт** — нет; ловушки только «спят/срабатывают».
- **Память раунда / накопительные счётчики** — нет.
- **Взаимодействие с колодой кроме добора** — нет; используй сброс.

## Что прочитать перед предложением новых идей

Перед тем как предлагать новую механику или карту, **просмотри оглавления**
в начале этих файлов (они содержат краткие списки уже разработанного):

- `mechanics/new-mechanics-ideas.md` — ~18 мета-механик (Deathrattle, Charges, Team Aura, Self-harm, Curses, Spare cost, On-Kill, On-Hit, Selfish→Ally Conversion и др.).
- `mechanics/new-cards-ideas.md` — ~20 идей конкретных карт (Засада лучника, Память предков, Кубитори, Кампо, Куноити, Военный совет, Wave и др.).
- `mechanics/aspect_matrix_draft.md` — матрица 100+ пересечений с метками ✓ Воплощено / ⚠ Отклонено.
- `mechanics/aspects.md` — словарь аспектов игры для построения матриц.

## Стиль предложений новых идей

1. **Флавор-обоснование** из японской истории/мифологии (правило №11). Японское имя с переводом приветствуется (Сосэй 蘇生, Кубитори 首取り, Куноити くノ一).
2. **Проверка по антипаттернам** из чеклиста выше.
3. **Связь с существующими картами** — указать родственников и в чём отличие.
4. **Целевое количество в колоде** (qty=1 для редких поворотных, 2+ для базовых).
5. **Faction-tilt** — самурайский / ниндзя / нейтральный, и почему.

## Стандартная посадка за столом

Игроки сидят **через одного** по фракциям: ниндзя—самурай—ниндзя—самурай.
Соседи слева/справа — почти всегда враги, союзник — через одного.
Это критично для дизайна позиционных карт. Подробнее — в
`meta_mechanics.md` №9, подраздел «Стандартная посадка за столом».

### `mechanics/` — дизайн-документы по механикам

Текстовые материалы по проектированию карт и баланса. Не код, не
исходники полиграфии — это пространство, где обсуждаются и фиксируются
правила дизайна.

- `cards.md` — текстовый реестр всех карт с типами и эффектами.
- `meta_mechanics.md` — мета-правила (North Star + 12+ правил +
  антипаттерны). Главный документ для любых решений по дизайну.
- `aspects.md` — плоский словарь аспектов игры (hp, trap, stance, charges
  и т. д.) для построения матриц «механика × аспект».
- `aspect_matrix_draft.md` — матрица 100+ пересечений аспектов с метками
  ✓ Воплощено / ⚠ Отклонено. Реестр дизайнерских решений.
- `new-mechanics-ideas.md` — копилка мета-механик (~18 пунктов). В начале
  файла — оглавление всех зафиксированных механик.
- `new-cards-ideas.md` — копилка конкретных идей карт (~20 пунктов). В
  начале файла — оглавление с типами и ядром каждой идеи.
- `character-themes.md` — темы персонажей (Blood, Restoration, Plague и
  т. д.) с четырьмя слотами (Draw / Trait / Deathrattle / Aura).
- `characters.md`, `characters-ideas.html` — финализированные персонажи и
  визуализация с iframe-превью.
- `asymmetry.md` / `asymmetry-drafts.md` — пары и черновики фракционной
  асимметрии.
- `low_full_card_ideas.md/.html` / `charges_cards_ideas.html` /
  `team_cards_ideas.html` — срезы идей по картам под конкретные
  механики (low/full HP контекст, Charges, командные карты).
- `fonts/` — копии шрифтов (Han-Zi, Salma Pro), используемых при
  оформлении карт.

## Формат предложений идей для существующих карт

Когда нужно предложить переработки/дополнения существующих карт под какую-то общую идею
(low/full HP контекст, фракционная асимметрия, ауры, новые типы эффектов) — формат
единый: **пара файлов в `mechanics/`**:

- `<тема>_card_ideas.md` — текстовый черновик с таблицей идей. Главный артефакт для
  обсуждения и git-diff.
- `<тема>_card_ideas.html` — визуальная версия с встроенными превью каждой карты через
  iframe. Дублирует данные из md, но позволяет смотреть на карту в момент чтения идеи.

Эталонный образец: `mechanics/low_full_card_ideas.md` и `mechanics/low_full_card_ideas.html`.

### Принципы отбора карт

- **Не охватывать всю колоду.** Брать только карты, где идея реально оживляет карту,
  а не натянута. Целевой объём одного среза — 10–15 карт.
- **Каждая идея сопровождается флавор-объяснением** (мета-правило №11). Короткая
  фраза-образ рядом с механикой: «Бенкэй несгибаем при полном здоровье», «последний
  капкан раненого зверя», «лекарь отдаёт последнее исцеление команде». Это сразу
  показывает, есть ли у идеи характер, или это сухая математика.
- **Прочерки допустимы.** Если для какого-то режима (low / full / самурай / ниндзя)
  идея неинтересна — ставится «—». Не натягиваем вариант ради заполненной клетки.
- **Сверка с мета-правилами.** Каждая идея проверяется хотя бы по правилам №6 (нет
  мёртвых карт), №8 (условие в момент разыгрывания) и №11 (флавор). Антипаттерны
  (например, дублирование существующей карты) — отклоняются.

### Структура HTML-версии

- Inline-стили, без зависимостей. Файл должен открываться двойным кликом.
- Таблица: первая колонка — карта (iframe-превью), остальные — варианты идей.
- Ширина первой колонки ≈ 320 px, iframe ≈ 300×470 px. Этого хватает на любую
  карту в колоде без вертикальной прокрутки.
- Если у одной карты несколько режимов (low/full, самурай/ниндзя, день/ночь и т. п.) —
  используется `rowspan` на ячейке карты, а варианты идут как отдельные `<tr>` с
  цветными бейджами и лёгкой подкраской фона ячеек, чтобы пары визуально группировались.

### Превью карты через embed

Приложение `app.html` поддерживает параметр `?embed=<ID>` — при нём UI скрывается
и показывается одна карта на белом фоне (см. `js/app.js`, секция «Embed-режим»).

- **ID карты** — из `js/cards.js` (свойство `id` у каждой записи).
- **Путь относительный:** `../app.html?embed=<ID>` (так HTML работает на любом
  диске и у любого пользователя).
- **Ленивый рендер:** `<iframe loading="lazy">`, чтобы прокрутка страницы не
  задумывалась, пока iframe-ы не попали в viewport.

### Что делать после черновика

- Идеи из `<тема>_card_ideas.md` живут как **черновик** до тех пор, пока не пройдут
  плейтест. После плейтеста выжившие переезжают в `js/cards.js` (правка `desc`
  существующей записи или добавление нового поля для контекстного режима).
- Параллельно стоит освежить `rules/rules.html`, если идея вводит новый термин
  (например, «full HP», «low HP») — иначе формулировки на картах останутся непонятными.

# Картотека карт — веб-приложение

Локальная картотека карточек. Открывается напрямую в браузере как статичный
HTML файл — без сервера, без сборки.

Приложение служит двум целям:
1. **Просмотр и фильтрация** карточек в браузере
2. **Подготовка к печати** — через `Ctrl+P` / диалог печати браузера карточки выводятся на бумагу в формате А4 по 9 штук (сетка 3×3). Карточки с тегом `trash` (как real-копии в родных группах, так и pseudo-копии в разделе «Корзина») в печать никогда не попадают — `wrapForPrint` фильтрует их до группировки, плюс есть CSS-страховка `.card-item[data-tags~="trash"] { display: none }` в `print.css`. Дополнительные опции печати (чекбоксы в нижнем ряду фильтр-бара): `Печать количеством` дублирует каждую карту по `qty`, `Печать рубашек` после каждой страницы фронтов добавляет страницу-зеркало с рубашками для duplex-печати (по группе: `media/backs/role.png` для ролей, `media/backs/character.png` для персонажей, иначе `media/backs/default.png`).
3. **CMYK soft-proof** — превью того, как карты будут выглядеть после офсетной печати по Fogra39. Включается двумя способами: чекбокс «🎨 CMYK preview» в строке опций печати (под рядом фильтров) или `?proof=cmyk` в URL (для шаринга ссылки). Оба пути подгружают `styles/proof-cmyk-baked.css` — палитру, прогнанную через ICC `Coated_Fogra39L_VIGC_300.icc` реальным lcms-engine'ом (sRGB → CMYK → sRGB). Этот вариант работает в любом браузере, потому что в CSS лежат обычные hex-значения. Альтернативный `proof-cmyk.css` использует спецификационный `@color-profile --fogra39` + `color()` — он оставлен в репо как future-proof для эпохи, когда браузеры догонят CSS Color 4. Без флага/чекбокса ни один из этих файлов не подгружается.

- **CSS** — чистый, без препроцессоров
- **HTML** — один файл точки входа

## База данных — cards.js

Экспортирует глобальный массив `const CARDS = [...]`.
Подключается до jQuery и app.js в app.html.

### Схема одной карточки

```js
{
  id: 1,                        // Уникальный номер
  title: "Катана",              // Русское название
  types: ["weapon"],            // Массив типов (см. допустимые ниже)
  qty: 2,                       // Количество в колоде
  desc: "Дальность 1, сила 2.", // Текст эффекта (поддерживает "-ИЛИ-")
  group: "weapon",              // Группа для разделителей (один тип)
  img: "cards/card_2_katana.png", // Путь к арту относительно app.html
  icons: ["melee1", "dmg2"],    // Иконки в верхнем-левом углу,
                                //   вертикальный стек
  iconsOr: ["ranged", "dmg1"],  // (опционально) Иконки альтернативной
                                //   ветки — стек заякорен в правом
                                //   нижнем углу карты. Порядок массива
                                //   не переворачиваем: array[0] вверху
                                //   стопки, array[last] в углу.
                                //   Обычно используется парно с
                                //   "-ИЛИ-" в desc.
                                //   Для weapon-карт с iconsOr рендер
                                //   также добавляет слой .card-bg-or
                                //   (media/weapon_bg_or.png) — оверлей
                                //   поверх weapon_bg, под card-art.
  titleBgColor: "#5d3c75"       // (опционально) переопределяет цвет
                                //   плашки заголовка для этой карты;
                                //   если не задан — берётся
                                //   GROUP_TITLE_COLOR[group]
}
```

### Допустимые типы

`role` | `weapon` | `trap` | `character` | `modifier` | `defense` | `stance` | `effect` | `intervention` | `aoe` | `action`

`role` — мета-карты сторон игроков (Ниндзя, Самурай); в колоде не участвуют,
рисуются отдельной группой в самом начале сетки.

### Конструкция «-ИЛИ-» в `desc`

Если в `card.desc` встречается подстрока `-ИЛИ-` (с любыми пробелами вокруг),
описание разбивается на несколько частей. Между частями вставляется
визуальный разделитель `.card-desc-or` — две градиентные линии и слово
«ИЛИ» по центру (компактный аналог `.group-divider` в палитре бумаги).
Само сочетание `-ИЛИ-` в текст не попадает.

Пример: `desc: "Атаковать оружием 2/1 -ИЛИ- передать карту союзнику."`
→ две строки текста, между ними «── ИЛИ ──».

Логика — в `buildDescContent()` в `js/app.js`, стили — в `styles/card.css`.

## Логика приложения — js/app.js

- `TYPE_META` — метаданные типов: label + color для тегов и фильтров
- `GROUP_TITLE_COLOR` — цвет верхней плашки по group
- `GROUP_ORDER` / `GROUP_LABELS` — порядок и названия групп-разделителей
- `buildCard(card)` — строит DOM-элемент `.card-item`
- `buildGroupDivider(groupKey)` — строит разделитель группы (полная ширина грида)
- `buildFilters()` — строит панель фильтров `#filter-bar`. Кнопки во
  втором ряду (типы карт) сортируются по убыванию количества карт с
  этим типом (`count(id)`, `qty` не учитывается, multi-type карта
  считается под каждым своим типом). Тай-брейк — стабильный порядок
  из `TYPE_META`. Так «Оружие» всегда первое, «Роль» — последнее.
- `buildStats()` — заполняет таблицу `#stats-table` в правом сайдбаре.
  Группы тоже сортируются по убыванию — по колонке «Карт» (сумма qty
  активных карт группы); тай-брейк — индекс в `GROUP_ORDER`.
  Псевдо-группы (Черновик, Корзина) идут после, в фиксированном
  порядке, без участия в сортировке.
- `isPlayable(card)` — вычисляемое на лету свойство (helper-функция,
  не хранится в данных карточки). Возвращает `false`, если
  `card.group` входит в `NON_PLAYABLE_GROUPS = ['role', 'character']`.
  «Игровые» карты — это активные карты (без trash и draft) минус роли
  и персонажи. В сайдбаре статистики показываем 4 числа:
  «Игровых типов / Игровых карт» (id `#stat-playable-{types,qty}`) и
  «Неигровых типов / Неигровых карт» (`#stat-other-{types,qty}`).
  В таблице групп процент в колонке «%» считается ТОЛЬКО от
  `playableQty`; неигровые группы (роли, персонажи) показывают «—»
  и помечаются классом `.stats-row--non-playable` (курсив, приглушённый
  цвет).
- `applyFilter()` — показывает/скрывает карточки и разделители, обновляет счётчик
- Фильтр: одиночный (один тип за раз), клик на активный — сброс к «Все»
- Зум: клик по `.card-item` → `transform: scale(2)` + `z-index: 100`, Escape/клик вне — закрыть
- Поделиться ссылкой: в zoom-режиме в правом верхнем углу карты
  появляется `.card-share-btn` (🔗). По клику ставит
  `location.hash = card-<ID>` и копирует полный URL в буфер обмена
  (через `navigator.clipboard`; fallback — `window.prompt`).
  Открытие страницы по ссылке вида `#card-<ID>` автоматически зумирует
  ту карту: `applyCardHashIfAny()` вызывается на старте и на каждый
  `hashchange`, при необходимости снимает фильтр (через `setFilter(null)`),
  если карта оказалась скрыта, и прокручивает её в видимость через
  `scrollIntoView({ behavior: 'smooth' })`.

## Внешнее состояние — kvdb.io

Backend'а у приложения нет, но при необходимости персистентного состояния
между пользователями/устройствами используем внешний KV-стор
[kvdb.io](https://kvdb.io) — простое хранилище ключ-значение поверх REST.
Ничего локально не сохраняется (никаких `localStorage`/`sessionStorage`).

### js/kvdb.js — обёртка над API

Подключается в `app.html` ПЕРЕД `app.js`. Экспортирует `window.KVdb`:

```js
var bucket = KVdb.bucket('BUCKET_ID', 'optional_access_token');

await bucket.get(key);                  // → строка | null (404)
await bucket.getJSON(key);              // → объект | null
await bucket.set(key, value, { ttl });  // POST text/plain
await bucket.setJSON(key, obj, { ttl });// POST application/json
await bucket.del(key);                  // DELETE (404 → null)
await bucket.incr(key, 1);              // PATCH +1, возвращает новое значение
await bucket.list({ prefix, values, limit, skip, reverse });
```

Все методы — Promise. `404` для `get/getJSON/del` трактуется как
«нет ключа» и возвращает `null`. Прочие не-2xx → `reject(Error)` с
полями `.status` и `.body`.

Лимиты kvdb: ключ ≤ 128 байт, значение ≤ 16 КБ, TTL по умолчанию
1 неделя (бесплатный план).

### Конфиг — KVDB_CONFIG

Перед подключением `comments.js` в `app.html` объявлен глобальный конфиг:

```js
window.KVDB_CONFIG = {
  bucket:   '',     // id bucket'а на kvdb.io
  writeKey: null    // опциональный write_key, если bucket приватный
};
```

Если `bucket` пустой — `comments.js` молча отключается с warning'ом.

### Как создать bucket (один раз вручную)

```bash
curl --data-urlencode 'email=YOU@example.com' https://kvdb.io
# → ответ: короткий id, его и пишем в KVDB_CONFIG.bucket
```

После создания **обязательно подтвердите email** по ссылке в письме —
без верификации kvdb блокирует записи (отвечает «email address not verified»).

### Комментарии — js/comments.js

UI:
- На каждой карточке в `.card-footer` появляется кнопка-бейдж
  `.card-comments-btn` с эмодзи 💬. Класс `.card-comments-btn--has`
  включается, если у карточки есть хотя бы один комментарий —
  бейдж становится золотым, и в правом верхнем углу появляется
  красный пульсирующий кружок (`::after`), как в мессенджерах
  при непрочитанных сообщениях. Само количество комментариев
  нигде не показываем: достаточно факта наличия.
- Клик по бейджу открывает оверлей `.comments-overlay`
  (fixed-position на `body`, не масштабируется зумом карточки).
  В оверлее: список комментариев + форма «Комментарий» + «Добавить»
  (без поля «Имя» — комментарии анонимные).
- Закрытие оверлея: кнопка «×», `Escape`, или клик вне панели.
  Escape-listener висит в capture-фазе, чтобы перехватить событие
  до document-level handler'а app.js (иначе зум закрылся бы вместе
  с оверлеем).
- Бейдж и зум независимы: клик по карточке зумит, клик по бейджу —
  открывает комментарии (с `e.stopPropagation()`, чтобы не зумить).

На старте модуль одним запросом `bucket.list({ prefix: 'card_' })`
(без `values=true`) получает только список ключей вида
`card_<ID>_comments`. По ID:
- помечает соответствующие `.card-comments-btn` как `--has`,
- проставляет атрибут `data-has-comments="1"` на `.card-item`
  (включая pseudo-копии в Корзине).

Тела массивов не качаем — это самый дешёвый сценарий по трафику.
При добавлении первого комментария к карточке метка обновляется
локально (без повторного `list`).

### Фильтр «💬 Комментарии»

После того как `loadCommentedCards()` отрезолвится, `comments.js`
добавляет в третий ряд `.filter-bar` кнопку `.filter-btn--comments`
с `data-type="__comments__"`. До успешной загрузки списка ключей
кнопки нет — фильтру нечем оперировать.

Логика фильтрации живёт в `app.js`: при `activeMode === '__comments__'`
карточка видна, если у неё `data-has-comments="1"`. Переключение делает
`window.CardFilter.toggleMode('__comments__')` — публичный API из
`app.js`:

```js
window.CardFilter = {
  setMode:    function (mode) { ... },  // установить или null = «Все»
  toggleMode: function (mode) { ... },  // повторный клик снимает фильтр
  getMode:    function () { ... },
  apply:      function () { ... }
};
```

`__comments__` добавлен в `VALID_MODES`, так что фильтр живёт и в
`location.hash` — закладка/перезагрузка сохраняют выбор.

Стратегия хранения:

| Что              | Где                                 |
|------------------|-------------------------------------|
| Ключ             | `card_<ID>_comments` (ID = `card.id`) |
| Значение         | JSON-массив объектов комментариев   |

Один комментарий:

```js
{
  date:    "2026-04-30T10:15:00.000Z",  // ISO, new Date().toISOString()
  comment: "Эта стойка слишком сильная" // текст
  // author: опционально и только для совместимости со старыми
  //         комментариями — новые пишутся анонимно
}
```

Комментарии пишутся анонимно: имя автора не запрашивается и не хранится.
Старые комментарии с полем `author` корректно отображаются (показывают имя),
новые — без имени, только дата. При записи нового комментария всегда сначала
перечитываем массив с kvdb, чтобы не затереть параллельные правки с другого
устройства.

### Удаление комментария

В каждом комментарии в правом верхнем углу есть кнопка `.comment-del` (×).
Клик → `window.confirm` → `deleteComment(cardId, commentDate)`:
1. Re-load массива с kvdb (защита от гонок).
2. Поиск элемента по полю `date` (ISO-строка с миллисекундами — практически
   уникальна) и удаление через `splice`.
3. Если массив стал пустым — `bucket.del(commentsKey)` полностью убирает
   ключ. Иначе `loadCommentedCards` при следующей загрузке увидел бы
   пустой `[]` и снова пометил карту как «есть комментарии».
4. Иначе — `setJSON` сохраняет урезанный массив.
5. UI перерисовывает список и зовёт `markBadge(cardId, list.length > 0)` —
   при удалении последнего комментария бейдж и `data-has-comments` снимаются,
   карта выпадает из фильтра «💬 Комментарии».

Из консоли доступен `window.CardComments` для отладки: `bucket`, `load(id)`,
`save(id, list)`, `keyFor(id)`.

### Когда использовать kvdb

- Комментарии, заметки, оценки карт от пользователей
- Любые шаренные между устройствами правки (TODO, тэги)
- Простые счётчики/метрики

### Когда НЕ использовать kvdb

- Большие данные (значение > 16 КБ) — не лезет в один ключ
- Конфиденциальные данные — bucket без `secret_key` доступен любому,
  кто знает id; для приватного хранения используйте `secret_key`+`read_key`
- Источник правды для самой колоды — она остаётся в `cards.js`
